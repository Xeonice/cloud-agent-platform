Synthesized from three parallel research routes (Web / Codebase / Archive), 2026-07-31. Each finding is attributed to the route that produced it. Section 4 draws out what the proposal must decide, adopt, or avoid.

## 1. Web route (external prior art & ecosystem constraints)

### 1.1 Ratchet mechanics (R3 baseline)

- **Betterer** is the JS-ecosystem reference implementation of the ratchet pattern: it snapshots current violations into a committed results file, fails CI only on new violations, and its documented endgame is "when the count reaches zero, graduate the rule into normal lint config and delete the test." (https://phenomnomnominal.github.io/betterer/, https://charpeni.com/blog/enforce-best-practices-incrementally-with-betterer) — validates the shrink-only baseline + "清空即验收" shape and offers a reference file format.
- **ArchUnit FreezingArchRule** is the canonical ratchet semantics design: first run stores violations, later runs fail only on unknown ones, and the store auto-shrinks so the baseline can never regrow; issue #676 settled that a fixed violation must never itself break the test. (https://www.archunit.org/userguide/html/000_Index.html, https://github.com/TNG/ArchUnit/issues/676) — answers the two design decisions 工件04§D leaves open: (a) auto-reduce vs manual-edit on fix, (b) whether a stale entry is an error.
- **ESLint v9.24 bulk suppressions** are the strictest fail-closed variant: `eslint-suppressions.json` records per-file/per-rule counts, and CI fails both on new violations AND on stale (unused) suppression entries, with `--prune` to clean. (https://eslint.org/blog/2025/04/introducing-bulk-suppressions/, https://eslint.org/docs/latest/use/suppressions) — matches the 元规则 "豁免默认空、空扫描即失败、fail-closed" more closely than ArchUnit's silent auto-reduce; count-based (not line-based) entries survive unrelated refactors.
- **dependency-cruiser** ships both halves of R3 off-the-shelf: tree-wide forbidden-dependency rules plus a known-violations baseline file (`depcruise --init baseline` → `.dependency-cruiser-known-violations.json`) explicitly designed so old violations don't bury new ones. (https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md, https://technology.lastminute.com/how-we-enforce-architecture-boundaries-at-scale-on-our-app/) — build-vs-buy datapoint; even if the hand-rolled .mjs gate is kept (it checks symbols, not just imports), its baseline JSON schema (ruleName + from/to pairs) is a proven format for `scripts/ratchets`.

### 1.2 Boundary-enforcement scope (R3 framing)

- The boundary-enforcement ecosystem (Nx enforce-module-boundaries, Sheriff by Softarc, eslint-plugin-boundaries) uniformly applies rules to the **whole source tree by default with explicit opt-out exemptions** — none scope enforcement to an allowlist of directories the way `sourceBoundaryRoots` currently does. (https://github.com/softarc-consulting/sheriff, https://nx.dev/docs/features/enforce-module-boundaries) — external validation that partial-scope boundary checks are an anti-pattern; Sheriff notably runs standalone via CLI, the same architecture as the repo's .mjs gate scripts.

### 1.3 Export-surface control (R6)

- Ecosystem consensus is that `export *` barrels leak internal symbols; the public edge of a package should use explicit named `export { x } from` lists — explicit exports define what is public, keep the rest implicitly private, and improve tree-shaking/compile-time. (https://tkdodo.eu/blog/please-stop-using-barrel-files, https://blog.coderspirit.xyz/blog/2022/11/06/export-barrels-considered-harmful/) — the R6 fix direction (explicit whitelist) is the industry default and also justifies deleting the 6 dead re-forwarding files.
- **Microsoft api-extractor** implements exactly the export-surface snapshot workflow: trace all exports from an entry point into a committed `.api.md` report; CI fails when actual surface diverges from the reviewed report, forcing an explicit review step for any surface change. (https://api-extractor.com/pages/setup/configure_api_report/) — adopt the tool or mimic the pattern (commit snapshot, diff in CI, update = deliberate reviewed act).
- **publint + @arethetypeswrong/cli (`attw --pack`)** are the standard CI gates for package.json exports/subpath correctness; a subpath export whose deps sit in devDependencies is precisely the consumer-side breakage class these tools catch. (https://publint.dev/rules, https://tsdown.dev/options/lint) — cheap to add (~3 lines) if the change wants a durable gate for the `./testing` devDep 归位 item, not just a one-off fix.
- **Knip** finds unused files, unused exports, and misplaced dependencies across monorepo workspaces, marketed as a CI regression gate. (https://knip.dev/explanations/why-use-knip, https://github.com/webpro-nl/knip) — the standing-gate candidate that prevents recurrence of both the dead-forwarding-file and devDep-misplacement classes (fits master-plan 总则 "兑现承诺").

### 1.4 CI semantics & required checks

- GitHub's required-status-check semantics make **paths-filtered workflows inherently hazardous**: a workflow skipped by paths filter leaves its required check "Expected — Waiting for status" forever and blocks merge. Documented workarounds: (a) paths-ignore mirror workflow with identically-named no-op jobs, (b) always-run workflow with in-job `if:` change detection (skipped jobs report Success), (c) a poll gate. Renaming a required job has the same block-forever effect until branch protection is updated. (https://github.com/orgs/community/discussions/44490, GitHub docs on troubleshooting required status checks) — grounds both scope-agent-context task 3.4's 双向观察 (must test touched AND untouched-path PRs) and the "required context 名字漂移只登记观察不改名" item.
- **Fail-on-empty-discovery is the ecosystem default**, not exotic policy: Jest deliberately exits non-zero when zero tests match (PR #5127 added `--passWithNoTests` as an explicit opt-out), and CI postmortems document glob drift silently running 0 tests for weeks. (https://github.com/jestjs/jest/pull/5127, dev.to postmortem) — external confirmation of 工件04§A "空扫描即失败" for R4's glob discovery and the agent-identity 补集扫描.

### 1.5 Discovery-based parity & CI test lanes

- The **conformance-suite pattern** (one shared suite discovered-and-run against every implementation, never per-implementation hardcoded lists) is how mature multi-driver ecosystems enforce parity — e.g. connectrpc/conformance runs the same suite against every implementation. (https://github.com/connectrpc/conformance) — R4's move from 3 hardcoded `PROVIDER_TEST_DIRS` to glob discovery is this exact pattern; a new provider package auto-enters the parity check with no registration step, which is what makes the fork/third-party provider 承诺 enforceable.
- **Playwright visual-regression CI practice** has converged on: generate baselines inside the pinned Playwright Docker image (Mac-generated baselines always diff against Linux runners due to font rendering), disable animations + mask dynamic content, treat baseline images as reviewed source code, and quarantine visual tests in a dedicated tagged step. (https://testquality.com/playwright-visual-regression-guide/, https://noraweisser.com/2026/02/01/visual-testing-with-playwright-and-docker/) — moving `test:visual` into CI requires deciding the rendering-environment pin **first**, or the gate flakes on OS font differences; the repo's OD-snapshot drift is the same "baseline drift" problem the "baselines are source code" practice addresses.
- **Storybook test-runner** establishes the "stories as executable CI smoke tests" precedent: every story becomes a Playwright-driven spec where render-without-error is the baseline assertion, with documented GitHub Actions recipes. (https://github.com/storybookjs/test-runner) — for terminal-stories 进 CI, the story file IS the discovered test inventory, consistent with 发现式 mapping.
- **Durable-execution systems** (Temporal, Restate, DBOS) treat kill-worker-with-in-flight-work-then-assert-resume as a first-class tested path: journal progress, kill mid-step, assert a restarted worker adopts and continues without duplication. (https://www.restate.dev/what-is-durable-execution) — industry confirmation that the stateful boot-smoke variant (restart with a running task seeded before boot) deserves its own automated CI variant; the repo's own provider-fill vs tasks-read 裂脑 bug was exactly the class clean-boot smoke and unit fakes both missed.

### 1.6 turbo.json hygiene

- `globalDependencies` entries feed file contents into the global hash invalidating every task's cache; documented use is real root-level config files, so a dead reference to a nonexistent `tsconfig.base.json` is pure hash-input noise with no protective effect — removing it is behavior-neutral. (https://turborepo.dev/docs/reference/configuration) — no external constraint blocks the fix; pairs naturally with "apps/api 接入 @cap-console/tsconfig" since a real shared tsconfig is exactly what globalDependencies is documented for.

## 4. Implications for the proposal

**A. Ratchet design decisions (R3) — decide up front, in the design doc**
