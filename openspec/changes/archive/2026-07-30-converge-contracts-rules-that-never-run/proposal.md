## Why

The previous change made every shared type have one declaration and built a gate
that keeps it that way. It also found the same defect twice on the way, and fixed
only the two instances it happened to touch:

```
SmtpConfigReadSchema            zero call sites → the api emitted a body its own
                                declared contract rejected
RuntimeReadinessResponseSchema  zero call sites → the api sent an envelope while
                                the contract declared a bare array, from the very
                                commit that introduced both (f050ab0)
```

A schema nothing executes cannot notice anything, so both drifted in silence for
months. The gate that shipped measures **import**-reachability — whether anything
names an export. That is a different property from whether anything *runs* it,
and the capability spec already states the missing one as a SHALL:

```
monorepo-foundation/spec.md:382
  WHEN a contract schema has no call site anywhere
  THEN it SHALL be reported
```

That scenario was written into the spec during the previous change's archive and
nothing implements it. **It is itself a rule that never runs.**

Measured on `81a115d`: of 371 schema declarations, roughly sixty are never
executed by production code. Three are being violated right now, and one of them
is the third instance of exactly the defect above:

```
AdminRevealResponseSchema   contract: { email, password } both required
                            api: admin-reveal.controller.ts:54,80 return {}
accounts local DTOs         accounts.service.ts:197 restates five contract schemas
                            and drops the contract's .max(200) password bound,
                            whose comment states it exists so a single field
                            cannot exhaust the argon2 hasher
mcp-token list envelope     api sends { tokens } and the contract declares it;
                            apps/web declares a bare array and carries
                            both-branch defensive code — RuntimeReadiness again,
                            with the sides swapped
```

None is a live vulnerability — the account routes are admin-gated and the OTP
code is generated by the api itself. They are drifts between a declared rule and
the enforced one, which is precisely the thing this package exists to prevent and
currently cannot detect.

## What Changes

- **The instrument is fixed before anything is scoped from it.** The shipped gate
  has two verified defects: its schema/type pair rule is bypassed by
  self-reference (a probe pair that nothing uses passes with exit 0), and it never
  scans `scripts/`, where sixteen files reference contracts — a blind spot that
  already falsifies one of its own exception reasons.
- **A second gate measures execution-reachability**: a contract schema that no
  production code parses, directly or through something composed from it, fails
  the build. It models the `/v1` operation table's `operation.input.<section>.parse`
  indirection explicitly rather than guessing, because a text-level probe reports
  at least eight false positives there.
- **The renamed duplicates that gate exposes converge.** Five local DTOs in
  `accounts.service.ts`, two in `otp.controller.ts`, and the mcp-token list
  envelope in `apps/web`.
- **BREAKING (behaviour, not wire shape)**: the api tightens onto the contract on
  two request surfaces. A password over 200 characters and an OTP code that is not
  six digits begin returning 400 where they were previously accepted. No field is
  added or removed and no response changes.
- **Declarations that are false or stated at a granularity nothing can consume are
  settled**, deleted or given a call site with the reason recorded either way.
- **`--test-force-exit` is removed from the two api suites** (user decision D5),
  because this change will claim "counts unchanged, no coverage lost" and that
  claim is currently footnoted by the previous change's own task 2.6.

Not in scope, and each recorded with where it belongs: the test-runner mount
change, the inline-literal restatements, epic Phase 1b, and publishing.

## Capabilities

### New Capabilities

None. This change implements a requirement `monorepo-foundation` already states
and adds the enforcement half of it.

### Modified Capabilities

- `monorepo-foundation`: the "a schema nobody executes is treated as unverified"
  scenario becomes a requirement with a gate behind it, and gains what the
  previous change learned by getting it wrong — that reachability must be measured
  through declared indirection points, and that a check must be shown to fail on
  the shape it is meant to catch, not merely on some shape.

## Impact

**Code** — one gate script plus its self-test; two corrections to
`scripts/contracts-shared-export-check.mjs` and a re-derived exceptions list;
seven local DTOs deleted across `apps/api/src/accounts` and `apps/api/src/auth-otp`;
the mcp-token list shape and its defensive branch in `apps/web/src/lib/api/real.ts`;
`AdminRevealResponseSchema` gains its absent arm and a call site; one deletion in
`packages/contracts/src/auth.ts`; two lines in `apps/api/package.json` and one in
`.github/workflows/ci.yml`.

**Behaviour** — two request surfaces tighten (above). Everything else is a
declaration change over bytes already being sent.

**Verification** — a converged declaration must change behaviour nowhere except
the two tightened surfaces, and those are verified against the pre-change tree
the way the previous change's task 3.5 was: the new cases must fail on the old
code, or they are not evidence.

**Non-Goals**

1. The inline-literal restatements (`'Bearer'` at roughly thirty sites, the
   `AUTH_TOKEN*` env-var names). They are recorded as gate exceptions with
   reasons. Converging them is cheaper before the repo split than after, but it is
   not what this change is about.
2. Any test-runner work beyond deleting the flag. The larger proposal was refuted
   on measurement — truncation corrupts the count and the diagnostic but never the
   verdict, so no defect ships green.
3. Publishing, module moves, or repository restructuring.
